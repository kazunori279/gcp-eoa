## Findings

- **P3 — Memory Bank rows = 0: ROOT-CAUSED (re-run 3) → fixed with a Step 2 hard gate.**
  On runs 2 & 3 the `…/memories` API returned **0 rows** (run 1 had 1). Root cause found on
  re-run 3: **M2 Step 2 only implemented session state, not Memory Bank.** `app/agent.py` had
  `set_home_station`/`get_home_station` (session-state, `{home_station?None}` injection) but
  **no `PreloadMemoryTool` and no `generate_memories` `after_agent_callback`** — so the agent
  never writes or reads long-term memory. (The deploy wrapper `agent_runtime_app.py` *does*
  wire `VertexAiMemoryBankService`, so the service exists — the agent just never uses it.)
  With no write path, the deployed agent stores zero memories and S2's "recall" is
  session-state bleed, exactly what the workshop's own ground-truth note warns about. This is
  the same non-determinism class as the Step-3 code-exec no-op (run 1 wired it, runs 2–3 did
  not). **Fix:** `m2.html` Step 2 now has a **hard-gate self-check** — do not report done until
  `grep` confirms both a `generate_memories`/`add_session_to_memory` `after_agent_callback`
  (write) AND `PreloadMemoryTool` in the agent's tools (read). Endpoint note: the memories
  query itself was correct all along (`{region}-aiplatform.googleapis.com/v1beta1/{engine}/memories`,
  HTTP 200 `{}` with a valid token) — unlike M5, this was a genuine missing-code issue, not a
  wrong-endpoint artifact.
  - **Re-drive validation (2026-07-24).** Re-drove Step 2 with the hard gate on a **fresh agy
    session** → agy added the wiring: `PreloadMemoryTool` (read) + an `after_agent_callback`
    (`auto_save_session_to_memory_callback` → `add_session_to_memory`, write), confirmed in
    `agent.py`; smoke green; re-deployed the engine. **The gate fixes the code-completeness
    root cause — the Memory Bank wiring is now guaranteed.** However, driving set-home
    (session A) then a new-session recall (session B) and polling `memories.list` for **~8 min
    still showed 0 rows**. So Memory-Bank *row generation* is **async/best-effort and was not
    reproduced** in this minimal 2-turn test (run 1's single row came from the richer
    multi-turn Step 6). Net: the **P3 code cause is fixed** (Step 2 can no longer silently skip
    Memory Bank); the **residual is platform async-generation latency/threshold**, already
    mitigated by the Step-6 settle note + the ground-truth check — not a workshop-code defect.
  - **Full Step-6 re-run + conclusive probe (2026-07-24).** Drove the complete multi-turn
    Step 6 against the redeployed engine — **all 5 cases PASS**, and S2 (new session) *appeared*
    to recall "Paris Nord," which agy attributed to `PreloadMemoryTool` / Memory Bank. But the
    API is **conclusively empty**: `memories.list` = `{}` for **~10 min**, and `memories:retrieve`
    returns **0 hits across every user scope probed** (`user`, `cli-user`, `default-user`, `""`,
    `test-user`). So **no memory was ever persisted** — S2's "recall" is **session context, not
    Memory Bank** (agy over-reported the mechanism, exactly what the ground-truth note guards
    against). **Bottom line:** the workshop code is now correct (wiring guaranteed + deployed +
    read path invoked), but **genuine Memory-Bank persistence is not reproducible in this
    environment** — `add_session_to_memory` yields no queryable rows. Run 1's single row remains
    the only observed write, unreproduced across runs 2/3 + two re-drives. This is a
    **platform-level Memory Bank behavior to escalate separately**, not fixable in the workshop
    prompts; the Step-6 ground-truth check correctly catches it.
- **P1 — Step 3 (code execution) can silently no-op.** On the first run agy read the DK
  MCP but made **no code change** and reported completion in 19 s; `BuiltInCodeExecutor`
  was absent (verified in `agent.py`). A re-run fixed it. Likely cause: adding
  `BuiltInCodeExecutor` alongside 5 function tools on one agent is a non-obvious ADK move,
  and the step's success wording lets agy "complete" without the edit. **Suggest** Step 3
  add an explicit self-check ("confirm `code_executor=BuiltInCodeExecutor()` is set in
  `agent.py` and show a trace where Python actually ran") so a no-op can't pass. Note it
  did coexist with the 5 tools without breaking function calling (smoke + deployed S1–S3
  still worked).
- **P2 — `agysend` premature markers on deployed/background steps (5, 6).** Deployed calls
  have long static waits that trip the stability detector; the step-6 transcript captured
  empty even though agy finished. Ground truth = the Vertex operation + the live pane +
  the memories API. (Harness: use a larger `stable` window, e.g. 40–60 s, for deployed
  steps; the eval used pane + API cross-checks instead.)
